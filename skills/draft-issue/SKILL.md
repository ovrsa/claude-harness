# 作業の前に Issue を下書きする

Claude Code は `/draft-issue <依頼>`、Codex は `$draft-issue <依頼>` で呼ぶ。Issue 番号の無いブランチに
初めて書き込むと、`hooks/lifecycle-pre-edit.js` がこのスキルを案内する（セッションに1回。止めない）。
流れの中の位置は `~/.claude/commands/COMMANDS.md` の「管理先があるプロジェクトの流れ」にある。

このスキルが書くのは、一時ファイルの下書きと承認の後の Issue だけ（1 で管理先の宣言を書く時を除く）。
実装は始めない。

## 1. 管理先を確かめる

```bash
node ~/.claude/scripts/resolve-tracker.js --repo .
```

- `configured` なら次へ進む
- `unconfigured`（終了コード 2）なら、`candidates` を示して人に選んでもらい、`expected_path` に書く。
  人が選ぶ前に起票しない
- `none` なら対象外。Issue は作らず、`docs/design/` の流れで進めると伝えて止まる
- `invalid` なら `error` を示して止まる

## 2. 大きさと重複を確かめる

- 1つの会話で終わらない依頼（ゴール文面が 4,000 字に収まらない、30ターンで終わらない）は、このスキルで
  起票しない。`/grill-me` → `/docs-build` で親 Issue を書き、`split-issue` で分ける
- 同じ成果を持つ開いた Issue があれば、起票せずにその番号を示し、`/start-issue <番号>` を案内する

```bash
gh issue list --repo <owner/repo> --state open --search "<依頼の要点>"
```

## 3. 欄を埋める

`~/.claude/templates/task-issue-template.md` の欄を、依頼の文面と環境（コード、テスト、既存の Issue）の
調査で埋める。事実は自分で調べ、人に聞かない。

欄ごとに、推測なしで埋められるかを判定する。**推測なし**とは、書いた内容の根拠を依頼の文面か環境の
どこかで示せること。

- 全部の欄を推測なしで埋められたら、**質問しない**（Grill を省く）。4 へ進む
- 埋められない欄があれば、**その欄だけ**を1回にまとめて聞く。1問ごとに推奨の答えと、その根拠を添える。
  埋まった欄は聞き直さない
- 答えから新しく決めることが出たら、それも欄の単位で聞く。欄に収まらない設計の決定が続くなら、
  1つの会話で終わる大きさではない。2 の最初の項目に戻る

推測で埋めやすく、外すと後で困る欄:

| 欄 | 推測なしで埋められる根拠の例 |
|---|---|
| 受け入れ条件 | 依頼が完了の状態を言っている。既存のテストや仕様が期待値を決めている |
| 検証方法 | 触る面を確かめるテストや検査が既にある |
| 制約・対象外 | 依頼が範囲を言っている。触ってはいけないものがリポジトリの規約にある |
| Graph | 人の判断が途中に要らず、別セッションで再開もしないなら「型: なし」 |

## 4. 下書きを整える

1. 本文をテンプレートどおりに書く。タイトルは成果を1行で書く。下書きは `mktemp -d` の下に置き、
   作業ツリーに残さない
2. `stop-ai-slop-jp` を通す
3. ゴール文面を作れるか確かめる。`INVALID` なら直して、もう一度確かめる

```bash
node ~/.claude/scripts/task-goal.js --repo . --check --input <下書き.json>
# 下書き.json: {"tracker":"github","task":{"ref":"draft","title":"<タイトル>","body":"<本文>"}}
```

## 5. 人のレビューを待つ

タイトルと本文の全文を会話に示し、承認を待つ。本文は Graph 節まで含めて人が読む。

- **人が承認するまで Issue を作らない。** 承認の言葉が無いまま次の手順に進まない
- 直す指示が来たら、直した本文をもう一度 `stop-ai-slop-jp` と `--check` に通してから、全文を示し直す
- 断られたら、起票せずに止まる

## 6. 起票する（承認の後）

```bash
gh issue create --repo <owner/repo> --title "<タイトル>" --body-file <本文>
```

先行 Issue や親 Issue があれば、`split-issue` の 4 と同じ手順で依存関係と親子関係を結ぶ。
他の管理先でも同じ本文を使い、その管理先の機能で作る。

作った Issue の番号とリンクを示し、次は `/start-issue <番号>`（Codex は `$start-issue`）から着手すると伝える。

## しないこと

- 承認の前に起票しない
- 起票の前に実装を始めない。下書きを作業ツリーに置かない
- 起票した後の本文を、人の確認なしに変えない
- upstream のスキル（`grilling` など）を編集しない。欄の質問で決まらない設計は `/grill-me` に回す

# linear-ticket-writeup

## 目的

Linear チケット（例 `RAR-2206`）の description に、変更やバグ対応の背景・概要を **短く** 記載する。読み手はレビュアーや将来の自分。過剰な詳細は書かない。

## 分量（最優先ルール）

- 全体で **概ね 15 行 / 600 文字以内**。長い説明は必ず削る。
- 見出しは最大 5 個。各見出しは **1〜4 行**。
- コードブロック・ログ全文・列マッピング等の細部は原則載せない（1 行の要約で足りる）。過去チケットの列挙も省略可。
- 詳細な検証ログや設計根拠は `docs/design/` / MR 側に置き、チケットには結論だけ書く。

## 更新の回数

- **description の更新は1チケット1回にまとめる。** 途中経過で書き換えない。結論が出てから書く。
- 途中で伝えることがあればコメントを1本足す。
- 理由: MCP の書き込みは送った本文をそのまま返すので、1回書き換えるたびに同じ全文が2回コンテキストに積まれる。実測では22チケットに `save_issue` を67回呼んでいて、それだけでセッションの14.5%を食っていた。コメント14回は1.6%だった。

## 見出しテンプレート（不要な見出しは省く）

```markdown
## 概要
1〜2文。何が起きて何を対応したか。

## 原因
1〜3行。根本原因を端的に。

## 対応
対象ファイル1行＋変更点を2〜4個の箇条書き。

## 手動作業
（あれば）人手で必要な作業を1〜3行。

## 検証
何で確認したかを1行。
```

## 記述ルール

- 事実ベース。実データ/実ヘッダーで確認した内容のみ書き、推測は書かない。
- 冗長表現を避ける。1 文 1 情報。
- ファイルパス・関数名・列記号（AE/AF 等）は原文のまま。
- MCP `save_issue` で更新する際は既存 description を確認し、意図せず消さない。
- 書き終えたら `stop-ai-slop-jp` を通す。特に false agency（「課題が浮き彫りになる」）と両論併記を潰す。

## 分量の目安（スケルトン）

各行の「」内は目安の長さ。実タスクの語彙で埋め、埋まらない見出しは削る。

```markdown
## 概要
「何が起きて何を対応したか」を1〜2文。

## 原因
「根本原因」を1〜3行。症状ではなく原因を書く。

## 対応
`対象ファイル`
- 変更点1（1行）
- 変更点2（1行）

## 手動作業
「コード外で人がやる作業」を1〜3行（無ければ節ごと削除）。

## 検証
「何で確かめたか」を1行。
```

## アンチパターン（やらない）

- エラースタックトレース全文の貼り付け
- 全列マッピング表や combined index の詳細列挙
- 「背景」節での経緯の長い説明（1〜3行に圧縮する）

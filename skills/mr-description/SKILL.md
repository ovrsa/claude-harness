# MR説明文の作成

## 目的

MRの説明文を決められたフォーマットで作成する。
**コードを読まずに書いてはいけない。実態と乖離した説明文はレビュー品質を下げる。**

---

## Step 1: 対象ファイルを全て読む（省略禁止）

MRに含まれる**全ファイル**を読む。ファイル数が多くても省略しない。

```bash
# MRに含まれるファイルを確認
git diff <base-branch>...<feature-branch> --name-only

# または各 worktree のコミット内容を確認
git show --stat HEAD
```

読む際に確認する観点:
- **何をしているか**（処理フロー・主要関数の役割）
- **設計上の判断**（なぜそのアプローチか、代替案はあるか）
- **依存・制約**（環境変数・外部API・GAS固有API等）
- **エラーハンドリング**（どのように失敗を扱うか）
- **テスト**（何を検証しているか、カバーできていない部分はあるか）

---

## Step 2: 書いた内容を実態と照合する（省略禁止）

説明文に書いた技術的な主張を、コードで裏付けられるか確認する。

チェック例:
- 「〇〇はエラー時に例外を投げない」→ コードで `muteHttpExceptions` や try/catch の実装を確認したか
- 「ユーザーごとにトリガーが独立する」→ `ScriptApp.newTrigger` の呼び出し箇所を確認したか
- 「即時削除」→ 本当に即時か、次回ポーリング時か確認したか
- スコープ名・定数名・関数名 → 実際のコードと一致しているか

**「だと思う」で書いた内容は必ずコードで確認してから書く。**

---

## Step 3: フォーマットに従って書く

以下の見出し構造を崩さない。

```markdown
# 概要
このMRが何をするかを2〜4行で説明する。
「何を」「なぜ」が伝わること。前後のMRがある場合はその関係も書く。

# タスク情報・リンク
- Linear: <チケットID>
- 前MR: <あれば>
- 後続MR: <あれば>
- 親チケット: <あれば>

# レビューしてもらいたい点
レビュアーに特に確認してほしい判断・設計・トレードオフを書く。
「〇〇という設計にした理由」「〇〇のアプローチが妥当か確認してほしい」など。
コードを読めばわかることではなく、**意図・背景・判断**を書く。

# 動作確認（どのように確認したか）
実際に何をして確認したかを書く。
- テスト: `npm test` 等のコマンドと結果
- 手動確認: 具体的な操作手順と期待した結果
確認できていない項目は「未確認」と明記する。

# 備考（レビュワーへの参考情報）
レビュアーが読む前に知っておくと助かる情報。
- 設計の前提・制約
- 意図的に省いた対応とその理由
- 関連する仕様・ドキュメントへのポインタ
```

## 各セクションの書き方ガイド

### 概要
- 「何を追加/変更/削除したか」+ 「なぜか」
- 実装の詳細（どうやって）はここに書かない
- 複数MRに分かれている場合は「このMRは〇〇まで。〇〇はRAR-XXXで行う」と書く

### レビューしてもらいたい点
避けるべき書き方:
- 「コードの動作を確認してください」→ レビュー自体がそれ
- 「全体的に見てください」→ 意味がない

良い書き方:
- 「〇〇という判断をしたが、△△という代替案もある。どちらが適切か確認してほしい」
- 「〇〇の設計意図を把握してもらいたい（背景: ~~）」
- 「〇〇の実装でGAS6分制限に引っかかる可能性があるか確認してほしい」

### 動作確認
- テストコマンドとその出力（Passしたこと）
- 手動確認は「〇〇を実行 → 〇〇が起きることを確認」の形で書く
- GASなど手動確認が必要なものは確認ステップを具体的に書く
- 確認できていない項目は正直に「未確認」と書く

---

## 注意

- 実態確認の手を抜かない。「だと思う」は書かない
- 専門用語・関数名・定数名は実際のコードと一致させる
- 「重要」「クリティカル」など強調語は多用しない
- MRが複数ある場合は各MRの独立性（そのMRだけ読んで理解できるか）を意識する

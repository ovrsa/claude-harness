# Pre-Plan Research Skill

## Purpose

実装計画を立てる前に、**まず専門家として自分の知識で考え**、その後必要な部分だけウェブで補完する。
ウェブ検索は「知らないことを調べる」ためではなく「判断を補強する」ために使う。

## Core Principle

```
Think First → Identify Gaps → Search Only Gaps → Synthesize → Plan
（まず考える → 不確かな点を特定 → その点だけ検索 → 統合 → プランへ）
```

---

## Workflow

### Step 1: 専門家として要件を分析する（検索前に必ず実施）

以下の観点で自分の知識を整理する:

```markdown
## 専門家分析

**要件の本質:** <何を解決するのか1文で>

**業界標準のアプローチ:**
- 一般的にはこういう方法が使われる: ...
- このプロジェクトのスタックに合う標準パターン: ...

**設計上のトレードオフ:**
- 方法A: メリット/デメリット
- 方法B: メリット/デメリット
- 今回の要件に合うのは: A or B、理由: ...

**自信のある部分:** ...（ここはウェブ確認不要）
**不確かな部分:** ...（ここだけウェブで補完する）
```

### Step 2: 不確かな点だけを検索する（最大2クエリ）

Step 1 で「不確かな部分」として挙げた点だけを検索する。
「なんとなく確認したい」は検索しない。

```
Query 1: <不確かな点1を英語で具体的に>
Query 2: <不確かな点2を英語で具体的に>（なければ検索不要）
```

検索不要な例:
- FastAPI の基本的なルーター設計 → 自分が知っている
- SQLAlchemy の async セッション管理 → 自分が知っている

検索すべき例:
- Supabase RLS と SQLAlchemy の組み合わせの既知の問題 → 実例を確認したい
- 特定ライブラリの2025年時点の推奨バージョン → 最新情報が必要

### Step 3: WebFetch で情報を抽出する（最大2URL）

```
このページから以下だけを抽出してください（箇条書き3点以内）:
1. <Step 1 の不確かな点> に対する推奨アプローチ
2. 避けるべきアンチパターン（あれば）
```

### Step 4: 統合サマリーを作成する

```markdown
## 調査結果サマリー

**専門家判断（確信度高）:**
- ...

**ウェブ調査で補完した点:**
- ...

**採用するアプローチ:** ...
**プランへの反映:** ...
```

---

## Token 効率化ルール

| ルール | 詳細 |
|--------|------|
| 自分の知識を先に出す | Step 1 なしに検索してはいけない |
| 検索は最大2クエリ | 「不確かな点」以外は検索しない |
| WebFetch は最大2URL | 公式ドキュメント優先 |
| 抽出は3点以内 | 必要な情報だけ指定する |

## 優先情報源

1. 自分の専門知識（最優先）
2. 公式ドキュメント（バージョン確認・APIリファレンス）
3. GitHub の実装例・CHANGELOG（既知の問題確認）

## アンチパターン

- **考える前に検索する**: Step 1 をスキップして Google に頼る
- **確認のための確認**: すでに知っていることを念のため検索する
- **調査の連鎖**: 検索結果から別のリンクを辿り続ける
- **ウェブの意見に流される**: 自分の判断より検索結果を優先する

## Example: 資材在庫管理のプラン前調査

```markdown
## 専門家分析

**要件の本質:** 資材の入荷→加工→現場使用の流れをトラッキングし、残在庫を把握する

**業界標準のアプローチ:**
- 在庫管理の標準: ロット管理 + 在庫移動履歴（Stock Movement）パターン
- 入荷・払出・使用それぞれをイベントとして記録するのが一般的
- 残在庫 = 入荷合計 - 払出合計（計算で導出、カラムに持たない）
- このプロジェクト (FastAPI + SQLAlchemy + Supabase) では
  Material → MaterialLot → StockMovement の3層が自然な設計

**設計上のトレードオフ:**
- 方法A (リアルタイム在庫数カラム): 更新が簡単だが整合性リスクあり
- 方法B (移動履歴から計算): 整合性が高いが集計クエリが必要
- 今回: 管理者のみが入力する運用なので B が適切

**自信のある部分:** データモデルの大枠、SQLAlchemy での実装方法
**不確かな部分:** Supabase RLS をロール別（管理者/従業員）に設定する際の制約

→ Query 1: "supabase RLS row level security role based access pattern 2025"
→ 検索結果: `auth.jwt() ->> 'role'` でロール判定が標準的と確認

**採用するアプローチ:** Material + StockMovement の2テーブル + RLS でロール制御
**プランへの反映:** 管理者のみ INSERT/UPDATE、全員 SELECT のRLSポリシーを設計に含める
```

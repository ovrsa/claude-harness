# C4 Rules

## 目的

改善後業務を支えるシステム構造を、第三者に説明できる粒度で残す。

- C4 は `業務フロー図` ではなく `システム観点の構造図` として使う
- 誰がどの順番で動くかではなく、どのシステムが何を責務として持つかを示す

## 基本方針

- Context と Container を標準にする
- Component は必要時のみ作る
- C4 は「問題発見の図」ではなく「解決策の構造図」として使う
- 1 図で 1 つの抽象レベルだけを扱う

## Audience

- Context: 非技術者を含む全体共有
- Container: 実装・運用に関わる関係者
- Component: 開発者と保守担当

Audience が曖昧なら、まず Context を作る。

## Context

### 必須要素

- 利用者
- 外部システム
- 自システム
- 主要な関係

### ルール

- 主要責務を短く書く
- 外部依存は省略しない
- 誰が何を利用するかを動詞で書く
- 業務課題やプロジェクト経緯は書かない

## Container

### 必須要素

- フロントエンド
- バックエンド
- DB
- 認証
- 通知
- AI/エージェント実行基盤
- 外部 SaaS

### ルール

- 各コンテナの責務を 1 文で書く
- 関係線は動詞で書く
- データの正本位置を意識する
- コンテナとコンポーネントを混ぜない
- デプロイ単位や運用責任を意識する
- UI、API、DB、外部依存を曖昧にしない

## Component

### 作る条件

- 複雑な判断ロジックがある
- AI orchestration がある
- 外部連携が複雑
- 保守境界を明示したい

### 作らない条件

- Container で十分伝わる
- 一時的な実装詳細しかない
- 読み手が開発者に限定されていない

## 品質チェック

- 誰向けの図かが明確か
- 境界が分かるか
- 外部依存が漏れていないか
- 責務が重複していないか
- 関係線のラベルが意味を持っているか
- 実装詳細を早すぎる粒度で書いていないか

## ラベルの書き方

- 要素名は名詞、関係線は動詞
- 技術名は補足として短く書く
- 責務説明は 1 文に収める
- 「管理する」「処理する」など曖昧語を避ける

悪い例:

- `システム`
- `データをいろいろ処理する`

良い例:

- `案件 API`
- `案件状態と承認フローを管理する`

## よくある失敗

- Context に内部コンポーネントを入れる
- Container 図に業務フローを混ぜる
- 関係線ラベルが `uses` だけになる
- DB の正本責任が曖昧
- 外部 SaaS をまとめすぎて何と連携するか分からない

## ツール標準

- ファイルは `.c4` 拡張子で作成する（VSCode で直接プレビュー可能）
- DSL ファイル（`.dsl`）は作成しない
- `.c4` ファイルに C4-PlantUML 構文で記述する

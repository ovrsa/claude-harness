# Diagram Review Rules

## 目的

図を「描けたか」ではなく、「第三者が判断に使えるか」でレビューする。

この文書は、スイムレーン、Mermaid sequence diagram、C4 の共通レビュー基準をまとめる。

## まず確認すること

- この図は誰向けか
- この図で何を合意したいか
- この図で何を捨てたか

この 3 つに答えられない図は、情報量に関係なく弱い。

## 共通レビュー基準

### 1. 単体で読めるか

- 口頭説明なしでも主旨が分かる
- タイトルだけで図の目的が分かる
- 凡例があれば、色や線種の意味が理解できる

### 2. 1図1目的か

- 問題発見の図と解決策の図を混ぜていない
- 業務フローとシステム構造を混ぜていない
- 上位粒度と詳細粒度を混ぜていない

### 3. 視線誘導があるか

- 読み順が自然に追える
- 主経路が最初に目に入る
- 補助情報が主役を邪魔していない

### 4. ラベルが意味を持つか

- 要素名は名詞、関係線は動詞になっている
- `uses` `request` `data` のような汎用語だけで済ませていない
- 読み手が業務語と技術語を結びつけられる

### 5. 情報量が適切か

- 図に載せるべき情報だけを載せている
- 詳細説明は別表や補助文書へ逃がしている
- セルやノードに長文を詰め込んでいない

## スイムレーンのレビュー基準

### 見るべき点

- 時間軸が一方向に固定されているか
- 特別な理由がない限り、縦軸が時系列（フェーズが行）になっているか
- 列が責任主体（担当・システム）ごとに切られているか
- フェーズ粒度が揃っているか
- 3層分離方式で描かれているか（背景塗り＋細い区切り線＋小さなタスクボックス）
- タスクボックスがマス全体を埋め尽くしていないか（マス内の余白で矢印が通れる）
- 1 ボックスに `① 〇〇 / ② 〇〇` と複数手順が詰め込まれていないか（タスク分離 + 矢印接続が原則）
- 空きマスにプレースホルダラベル（`未関与` `主担当ではない` `結果待ち` `参照のみ`）が置かれていないか（原則は空白）
- レーンをまたぐ矢印に番号付きラベル（`① ② ③ …`）でグローバル順序が示されているか
- 矢印ラベルに白背景（`labelBackgroundColor`）が付いていて、他要素と重ねても読めるか
- 条件分岐が独立したひし形ノード（`rhombus`）として描かれているか（タスクボックス内の `◇` 文字や `判定` 埋め込みは NG）
- 主経路と例外が見分けられるか
- 待ち、手戻り、二重入力が図上で認識できるか
- ツールやサービスの使われ方が認識できるか
- ツール表現が主経路を壊していないか

### 良い図の状態

- 現状図なら、どこが詰まっているかを 30 秒で言える
- 改善後図なら、何が減り、何が人に残るかを 30 秒で言える
- 青矢印だけ追えば代表シナリオを説明できる

### よくある失敗

- 比較のために無理に軸を揃えて読みにくくなる
- 空セルにプレースホルダラベルを並べて主経路が埋もれる
- 課題メモが主経路より目立つ
- 条件分岐をタスクボックス内に `◇` で押し込めて分岐先が読み取れなくなる
- 1 ボックスに `① ② ③` と複数手順を詰めて、視線が一度ボックス内に降りる必要が出る
- Excel やメールが重要なのに図から消えている
- ツール表現を増やしすぎて、かえって主経路が読めなくなる
- ツールを右端へ追い出しすぎて、工程との対応が読み取りにくくなる

## C4 のレビュー基準

### 見るべき点

- Context は利用者、外部システム、自システムの関係に絞れているか
- Container は責務境界が読めるか
- Component は本当に必要な内部責務だけに絞れているか
- データの正本や責任位置が曖昧でないか
- 外部依存と内部責務が混ざっていないか

### 良い図の状態

- Context を見れば「このシステムは何者か」が説明できる
- Container を見れば「どこをどう実装・運用するか」が説明できる
- Component を見れば「どこで変更影響が出るか」が説明できる

### よくある失敗

- Context に内部実装を入れる
- Container に業務フローを入れる
- Component が Container の言い換えになる
- 関係線ラベルが generic すぎる

## Mermaid sequence diagram のレビュー基準

### 見るべき点

- 1 図で 1 シナリオに絞れているか
- participant が責務境界で切られているか
- メッセージが具体的で、API / job / query の粒度が分かるか
- 同期処理と非同期処理が区別できるか
- `alt` `opt` `loop` `par` の使い分けが自然か
- 例外やタイムアウトが主経路を壊さずに表現されているか
- 図の前提条件が Note や補助文で補われているか

### 良い図の状態

- 開発者が見て、どこで待ち、どこで戻り、どこで非同期に切れるかを説明できる
- 実装責務の境界が分かる
- C4 では分からない相互作用上の判断が補われている

### よくある失敗

- participant を増やしすぎて読み手が迷う
- `request` `process` のような抽象ラベルだけで済ませる
- 成功系と例外系を 1 図に詰め込みすぎる
- 同期呼び出しとキュー投入が同じ見え方になる
- シーケンス図で構造説明までやろうとして C4 と役割がぶつかる

## レビュー時の優先順位

1. 正しい図法か
2. 単体で読めるか
3. 目的に対して十分か
4. 比較しやすいか
5. 見た目が整っているか

比較性や見た目は重要だが、可読性と目的適合性より上には置かない。

# Swimlane Rules

## 目的

第三者が見ても、順序、責任、判断、handoff が分かるマトリクス型スイムレーンを作る。

## 正本の扱い

- スイムレーン図の原本は Draw.io (`.drawio`) にする
- Markdown や README に図を載せる場合は、原則として Draw.io 原本への参照と補助説明に留める
- Mermaid はレビュー用の下書きに使ってよいが、最終成果物の正本にはしない
- 現状図と改善後図は、1 つの `.drawio` ファイル内の別ページ、または対になる 2 ファイルのどちらかで管理する

## 軸の標準

標準は `担当・システム（列） × 業務フェーズ（行）` のマトリクスにする。

- 横軸（列）: 役割、部門、システム
- 縦軸（行）: 業務フェーズ
- 時系列は原則として上から下に流す
- フェーズ間の遷移は行ヘッダ間を縦に進む

これにより、

- どのフェーズで
- 誰が
- 何を担うか

を一目で追える。単純な流れ図ではなく、原則としてマトリクスを使う。

## レーン設計の禁止パターン

| ❌ NG | ✅ OK |
|-------|-------|
| 「実務担当」「担当者（個人名）」のような人名・包括レーンを作る | レーン = 役割 / 部門 / ツール / システム / サービス境界（例: GAS / Redash / Zoho） |
| 1レーンに全フェーズのタスクが集中する設計 | 各レーンは「そのツール・主体が使われるフェーズのみ」にタスクが入る |
| 「判断」「確認」専用レーンを作り、そこにゲートウェイを集める | ◇ゲートウェイは確認が発生する主体のレーン内に配置する |

人を入れる場合: 承認者・W チェック担当など「他レーンと明確に責任が分離している役割」のみ可。担当者名は入れない。

## ツール / サービスの見せ方

ツールやサービスは主役ではないが、分散管理、二重入力、依存関係を見せるために重要である。表現方法は次の順で選ぶ。

1. セルの近くに小さな補助ボックスとして置く
   - どの工程でどのツールを触るかを最短で伝えたい
   - Excel、Mail、Calendar、ATS などの道具を見せたい
   - 主経路を崩さずに補助情報として添えたい

2. `担当・システム` の列として置く
   - システムが実際に状態を持つ
   - 更新や同期の責任を持つ
   - DX の改善論点として重要

3. セル内ラベルや注記としてだけ置く
   - 使っていることだけ分かれば十分
   - 図を軽く保ちたい

末尾の補助列は、ツール群を一覧化する必要が明確な場合だけに使う。標準にはしない。

アイコンは必須ではない。簡易な四角ラベルでもよい。重要なのは、`どこでそのツールを使うか` と `それが分散や転記の原因か` が伝わること。

## 現状図と改善後図の比較原則

- まず優先するのは、各図が単体で読めること
- 現状図と改善後図のレーン順、フェーズ順は、比較しやすいなら揃えてよい
- ただし、揃えることで不自然になるなら無理に合わせない
- 改善後でフェーズや主体が大きく変わるなら、読みやすい配置へ組み替えてよい
- 消えたフェーズや主体は、図の中に無理に残さず、タイトルや注記で変化を補足する
- 比較は `2枚を見比べて理解しやすいこと` を目標にし、`完全な座標一致` は求めない

## 使う前提

- 対象業務の開始条件と終了条件が定義できる
- 主要な責任主体が分かる
- 通常フローの順序が追える

この 3 点が曖昧なら、先に `templates/swimlane-intake-template.md` を埋めて工程棚卸しを行う。

## 実装前設計（必須）

`.drawio` を一切編集する前に、以下を Markdown の表で提示しユーザーの承認を得る。

1. レーン一覧: レーン名 / 主に使うフェーズ の表
2. セル内容: レーン × フェーズ ごとにタスクを 1 行 1 タスクで列挙（連番 `① ② ③` で 1 セルにまとめない。描画時に 1 ボックス 1 タスクへ分割される）
3. 矢印一覧:
   - レーン跨ぎ handoff（番号付きラベル）: 種類（主経路／NG／前提）/ 経路 / 番号ラベル
   - レーン内タスク間（番号なし）: 経路のみ
4. 判断ノード: 独立ひし形として配置することを宣言（タスクボックス内 `◇` は禁止）
5. 空きマス方針: 原則空白を宣言（プレースホルダラベル禁止）
6. グリッド方式: 3層分離（背景＋区切り線＋小タスクボックス）を採用することを宣言する

承認を得てから実装する。承認なしに XML を書き始めてはならない。

## グリッド方式

スイムレーン本体は「3層分離方式」を標準にする。マス＝大きな塗りつぶしボックスにしない（矢印・ラベルがセル本文と衝突するため）。

- 層1（背景）: 全体枠 / 列ヘッダ行・行ヘッダ列の塗り / フェーズ行の交互塗り
- 層2（区切り線）: 1 px の細長い矩形を vertex として描く（edge ではない）
- 層3（タスクボックス）: 各マスの中央に小さく配置し、マス内に余白を残す

詳細な mxCell スタイル例は [swimlane-drawio-style.md](./swimlane-drawio-style.md) を参照。

## 必須ルール

### 1. 時間は一方向

- 第一標準は上から下（行=フェーズ）
- 例外として左から右を採用してもよいが、混在は禁止
- 1図の中で時間方向を混在させない

### 2. レーンは責任主体ごと

- 人
- 部門
- システム
- 外部主体

レーンは「誰が主責任を持つか」で切る。ツール名だけでは切らない。ただし、ツールやサービスが実質的に状態管理や同期責任を持つ場合は、システム列として独立させてよい。

### 2.5 フェーズ見出しを置く

- 行見出しは業務フェーズ名にする
- フェーズ名は短く、必要なら 2 行までに収める
- 詳細な手順ではなく、まとまりとして読める粒度にする
- 比較しやすいなら現状図と改善後図で近い命名にする
- ただし、改善後でフェーズ統合や削除が起きるなら、無理に同じ名前へ寄せない
- 大きな差分は図タイトルか注記で補う

### 3. 開始と終了を必ず置く

- 開始条件が曖昧なら図にしない
- 終了条件が曖昧なら改善後比較ができない

### 4. 判断は独立したひし形ノードで表現する

- 条件分岐は独立した ◇ ひし形ノード（`rhombus`）として描く
- タスクボックス内に `◇` 文字や `判定` を埋め込む書き方は使わない
- ひし形には `何を見て分けるか` を短く書く（例: `承認可否` `在庫有無`）
- 分岐先は矢印ラベル（OK / NG、Yes / No、条件名）で識別する
- 判断理由の長文は図に書かない
- ひし形は判断責任を持つ主体のレーン内に配置する

### 5. handoff を明示する

- レーンをまたぐ遷移は重要論点
- handoff が多い箇所はボトルネック候補として扱う

### 6. 1図1粒度

- 同じ図で上位工程と詳細工程を混ぜない
- 粒度が混ざると第三者が読めなくなる

### 7. 例外フローも同じ図で扱う

- 現状図と理想図の合計 2 枚に収める
- 例外は別ページへ逃がさず、同じ図の中で色や破線で区別する
- ただし本流を壊すほど複雑なら、例外情報を減らして通常フロー優先に戻す

## 推奨セル型

- `start / end`
- `task cell`（矩形）
- `decision node`（独立した ◇ ひし形 / `rhombus`）
- `approval node`（独立した ◇ ひし形 / `rhombus`）

approval も decision も、task に埋め込まず、独立したひし形ノードとして描く。

## セル内タスクの粒度

1 マス＝1 ボックスにせず、複数手順がある場合はタスクを分離して矢印でつなぐ。

- 1 タスク = 1 ボックス（矩形）
- ボックス内テキストは動詞句のみ（例: `Excel記入` `メール送付`）
- 連番 `① ② ③` はボックス見出しに付けない（順序はフロー矢印で読める）
- レーン内の隣接タスク間は細い矢印で接続（ラベル省略可）
- レーンをまたぐ handoff 矢印は番号付きラベル（`① 申請メール` `② 承認連絡` 等）でグローバル順序を示す
- 1 マス内のタスクが 5 つを超えるなら、粒度が細かすぎるか、分岐ページへ逃がす候補

### セル内テキストの禁止パターン

| ❌ 書いてはいけないもの | 代わりに |
|----------------------|---------|
| 1 ボックスに `① 〇〇 / ② 〇〇` と並べる | 各手順を独立ボックスにし、矢印で接続する |
| 背景・理由の説明文（「〜なので〜する」） | 手順の動詞句のみ（「〇〇を確認」「〇〇をコピー」） |
| NG 時の対処手順をボックス内に詰め込む | ひし形ノードの NG 矢印ラベルに簡潔に記載 / 分岐ページへ |
| 「〜に注意」「〜の場合は〜」の条件分岐 | 独立したひし形ノード + OK/NG 矢印で表現する |

## 図に載せるもの

- フェーズ見出し
- レーン見出し
- 開始
- 終了
- task cell
- decision cell
- approval cell
- handoff
- 必要ならツール / サービス表現

## 図に載せすぎないもの

- 詳細な入力項目
- 長文の判断条件
- KPI 値
- A/B/C の詳細説明
- システム責務の詳細

これらは別表に逃がす。

## 空きマスの扱い

- 空きマスはそのまま空白にする
- `未関与` `主担当ではない` `結果待ち` `参照のみ` などのプレースホルダラベルは置かない（情報量に対してノイズになり、主経路を埋もれさせる）
- 「触らない」「関与しない」は背景塗りや列・行配置で十分に伝わる
- 例外: その空白が業務上のボトルネック（長時間の待ち・宙ぶらりんの状態）として議論したいときに限り、短い灰色ラベルを置く（例: `48h 待機` `承認停滞`）
- 灰色フィルでマス全体を塗りつぶさない

## ラベルの書き方

- ノード名は動詞ではじめる
- 1 ボックス 1 つの目的に絞る
- レーン名は役割か組織名にする
- ツール名を工程名に混ぜない
- 条件文は短くする
- 1 ボックスに複数手順を `① ② ③` で詰め込まない（ボックス分割 + 矢印で表現）

悪い例:

- `現場担当者がExcelで確認して上長へ連絡する`
- 1 ボックスに `① 在庫を確認する / ② 上長へ連絡する`

良い例:

- `在庫を確認する`（独立ボックス）
- `上長へ連絡する`（独立ボックス）
- 2 つのボックスを矢印で接続

## 補助メモで持つもの

- 使用ツール
- 入力
- 出力
- 正本
- 待ち
- 手戻り
- A/B/C 仮説

## 矢印

第三者が追えるように、矢印は 4 種を使い分ける。

| 種類 | 意味 | スタイルの目安 |
|------|------|----------------|
| フェーズ間 | 上→下の時間軸 | 灰・点線・細め・行ヘッダ間 |
| 主経路 | 初回／代表のハッピーパス | 青・太め・塗り矢じり・短文ラベル可 |
| 前提 | 「下の処理が動く土台」（同時刻の厳密順序と誤解されうるもの） | 紫・破線・開いた矢じり |
| 停止・例外経路 | 運用が止めたときの流れ | 赤・破線 |

Z 順: エッジをセルより前（XML 上は先）に置き、線がボックスの下に回るようにして文字を優先する（ツールで崩れたら手直し）。

詳細な `mxCell` の style 文字列例は [swimlane-drawio-style.md](./swimlane-drawio-style.md)。

### 矢印ラベルの書き方

- 青矢印は主経路
- 紫破線は補助・前提・例外補足
- 赤破線は待ち・停止・滞留・NG 差戻し
- レーンをまたぐ矢印には番号付きラベル（`① ② ③ …`）でグローバル順序を示す
- レーン内のタスク間矢印はラベル省略可（順序は配置で読める）

悪い例:

- `handoff`

良い例:

- `① 申請メール`
- `② OK: 承認連絡`
- `③ 例外案件を承認へ回す`

## レイアウト品質

- 列間・行間に最低でも十数 px の溝を取る（密着させない）
- 列幅は本文行数に合わせて伸ばす。本文は fontSize 10〜11 で統一しやすい
- タスクボックスはマス全体を埋めず、上下左右に 15〜25 px の余白を残す（矢印・ラベルが通る空きを確保する）
- 空きマスは原則として空白のまま残す（プレースホルダラベルを置かない）
- 例外的に空白に意味付けしたい場合のみ、中央に小さい灰色ラベル（120×30 程度、`48h 待機` `承認停滞` などボトルネック表現）を置く
- 矢印ラベルは必ず白背景（`labelBackgroundColor=#ffffff`）を付け、タスクボックスや背景塗りの上を通っても文字が埋もれないようにする
- 矢印はタスクボックス間（vertex 間）でのみ接続する。背景塗りや区切り線を source / target にしない
- 図上部に凡例: 列・行・各色矢印・セル内番号の意味・用語（例: GAS＝Google Apps Script）
- 脚注: 変更シナリオ（再申請・直接編集など）とメンテ方針
- できるだけ通常フローを一直線で追えるようにする
- 矢印の折り返しを増やしすぎない
- 交差が多いなら粒度を上げるか別図に分ける
- レーン数が多すぎるなら主要主体だけに絞る
- セル本文は 3 行から 5 行程度に収める
- 縦軸と横軸の見出しを必ず置く
- 全セルを完全に埋めようとせず、意味のある空きマスを残す
- 現状図と改善後図の位置合わせは、可読性を損なわない範囲でだけ行う

## 分岐ページ（任意）

- スイムレーンの特定セルの中身を、ひし形＋Yes/No ラベルで展開する
- 冒頭に副題で「スイムレーンのどこを拡大したか」を書く
- 各ノードに ①② や「誰が／何が起きるか」の平易語を足す
- 分岐は方向非依存なので、本図の縦時系列と無理に合わせなくてよい

## 既存ドキュメントとの役割分担

| 資産 | 役割 |
|------|------|
| 本 draw.io | レーン × フェーズの責任と代表経路 |
| シーケンス図（例: design.md） | メッセージ順・API 細部・エッジケース |
| README / 運用手順 | 操作手順・トラブルシュート |

矛盾時の優先順位: コードと design.md を優先し、図を更新する。

## よくある失敗

- 部門、役職、ツールが混ざったレーン設計
- task と decision の混在
- 例外を別ページ前提で設計する
- 例外フローを本流に詰め込みすぎる
- 正本や待ち時間を全部図に載せようとする
- 上位工程と詳細工程の粒度が混在する

## 検証チェックリスト（出す前に）

- 第三者が矢印だけ追って主シナリオを説明できるか
- 「誰が何もしない」マスに理由があるか
- 略語に凡例または初出説明があるか
- 分岐はスイムレーンで無理に詰め込んでいないか（必要なら分岐ページに逃がしたか）
- 時系列を追えるか
- 責任主体が明確か
- decision cell が判別できるか
- handoff が見えるか
- 通常フローが一目で追えるか
- テキスト量が多すぎないか
- 例外が本流を壊していないか
- レーンをまたぐ矢印に番号付きラベル（`① ② ③ …`）が付いているか
- 矢印ラベルが他要素と被って読めない箇所がないか（`labelBackgroundColor` を確認）
- タスクボックスがマスを完全に埋めて矢印と衝突していないか
- 1 ボックスに `① 〇〇 / ② 〇〇` と複数手順を詰め込んでいないか（タスク分離 + 矢印接続が原則）
- 空きマスにプレースホルダラベル（`未関与` `主担当ではない` `結果待ち` `参照のみ`）を置いていないか（原則は空白）
- 条件分岐がタスクボックス内の `◇` 文字ではなく、独立したひし形ノードで描かれているか
- Draw.io 原本の場所が README や補助文書から辿れるか

# テストスイート削減設計

## 背景

ハーネスのテスト資産は、`tests/` 配下の JavaScript が合計 26,515 行あり、本体の `scripts/` と `hooks/` の JavaScript 15,651 行を上回っている。通常の `npm test` は実測約 3.6 秒だが、`test:hooks` は約 73 秒を要する。特に `tests/hooks/hooks.test.js` は 5,783 行で、実装の偶発的な癖、既知不具合、内部ソース形状、重複する境界値を含んでいる。

問題は実行時間だけではない。現在のテストは、ハーネスが守るべき契約と、現時点の実装詳細を同じ強さで固定している。そのため、本体を安全に変更するための資産というより、テスト自身を維持する負担になっている。

## 決定

テスト資産を契約中心に再設計する。安全性、ライフサイクル、永続化、タスクルーティング、主要 hook・CLI、配布物の衛生に関する契約だけを明示的に残し、それ以外の重複・実装詳細・偶発的挙動を固定するテストを削除する。

削減の主目的は保守量の低減である。実行時間短縮は副次的な成果として扱う。

## 目標

- テストコードを 26,515 行から 7,955〜13,257 行へ削減する
- 各テストが守る契約を説明できる状態にする
- 同じ振る舞いを複数の層で重複検証しない
- 既知失敗の許容と suite 未登録テストをなくす
- 本体の実行時挙動を変更しない
- 削減後も安全境界と主要ライフサイクルを再実行可能な形で検証する

## 非目標

- 本体コードの不具合修正
- 網羅率の最大化またはカバレッジ率の数値目標
- すべての入力型・境界値・例外文言の固定
- テストフレームワークの全面移行
- ハーネスの機能追加

## テスト資産の構造

残すテストは次の 3 層に限定する。

### 1. 構造検証

設定、hook 登録、artifact 形式、配布対象、個人情報や秘密情報の混入防止を検証する。個人情報には、氏名、メールアドレス、ユーザー名、ローカル絶対パス、端末・アカウント識別子を含める。意図的な placeholder と test fixture は明示的な allowlist で区別する。構造検証はファイル内容を見ることがあるが、内部実装の書き方ではなく、外部から必要な宣言や形式だけを対象とする。

### 2. 契約テスト

入力と出力、状態遷移、権限判定、永続化結果など、利用側から観測可能な契約を検証する。unit テストは、複雑な判断ロジックまたは安全境界に限定する。

### 3. Smoke テスト

代表的なハーネス実行が端から端まで成立することを検証する。複数コンポーネントを横断する振る舞いは smoke または integration で 1 回だけ確認し、同じシナリオの unit・CLI・hook 重複テストは残さない。

## 残す契約

### 安全性

- 破壊的または高権限の操作を無承認で許可しない
- 読み取り専用操作と変更操作を区別する
- 配布物に個人情報、秘密情報、runtime 専用データを含めない

### ライフサイクル

- 非自明な変更では承認済み plan を要求する
- review、verification、必要な observation のゲートを守る
- 未完了または blocked の状態を完了として扱わない

### セッションと永続化

- セッション状態を保存し、同一 repository の状態として復元できる
- SQLite の主要 schema と書き込みが冪等である
- 欠損または破損した補助データでハーネス全体が危険側へ倒れない

### タスク判定

- タスクをリスク、権限、承認状態に応じて振り分ける
- credential、deploy、push、破壊操作、残存リスク判断を自動委譲しない

### Hook と CLI

- 主要な正常系が終了コード 0 で完了する
- 代表的な入力不正または外部依存の失敗を安全に扱う
- harness status と pipeline の主要出力が利用側の契約を満たす

## テストの採用基準

各契約には原則として次だけを残す。

- 代表的な正常系 1 件
- 代表的な入力不正 1 件
- 安全性またはデータ損失に関わる失敗系
- 意味のある境界値を最大 1 件

新しいテストは、上記の残す契約のどれに対応するかを説明でき、かつ起こり得る回帰を防ぐ場合だけ追加する。単に未通過行を実行するためのテストは追加しない。

## 削除基準

次のテストは削除する。

- `source.includes(...)` など、内部実装の文字列や書き方だけを検査するもの
- `Round 20`〜`Round 125` のように後付けで増殖した、契約外の境界値
- `null` の型強制、暗黙変換、例外文言など、偶発的な現挙動を固定するもの
- unit、CLI、hook、integration 間で同じ振る舞いを重複検証するもの
- 既知失敗のうち、古い期待または残す契約と重複しているレガシーテスト
- suite に登録されておらず、残す契約にも対応しないテスト
- 実装上の不具合を「現在の正しい挙動」として固定するもの

## Suite 管理

テストファイルと suite 所属は単一の catalog を正とする。`core`、`hooks`、`pipeline`、`regression`、`full` は同じ catalog から構成し、suite ごとの独立したファイル一覧は持たない。

catalog と実ファイルの差分を検証し、次をエラーにする。

- catalog に存在しないテストファイル
- 存在しないファイルを参照する catalog エントリ
- `full` から漏れる有効なテスト

`KNOWN_BASELINE_FAILURES` のような許容済み失敗は廃止する。ただし、既知失敗であること自体は削除理由にしない。各項目を次のいずれかへ分類し、disposition を記録する。

- 契約外または古い期待: 根拠を記録して削除する
- 残す契約の重複検証: 代表テストへ統合する
- 残す契約への実装違反: 追跡 ID を付けた別タスクを prerequisite として作り、その修正が完了するまで削減完了をブロックする

契約自体を保留または変更する必要がある場合は、本設計の承認要件変更として人間の再承認を得る。残存リスクの承認だけで、承認済みの安全契約を検証対象から外してはならない。

catalog の各テストには `required` または `optional` を付ける。各「残す契約」には、標準 verification 環境で実行される `required` テストを最低 1 件対応付ける。`optional` は追加の環境・platform 検証に限り、契約の唯一の検証にはできない。標準 verification 環境では `required` テストの skip を認めない。`optional` は対象環境、実行条件、skip 理由を catalog に持ち、実行時の skip 件数を verification evidence に記録する。

## 変更可能範囲

変更してよい範囲は次に限定する。

- `tests/` 配下のテスト、catalog、runner
- `scripts/ci/` 配下の test-only validator
- `package.json` の test script
- README のテスト実行説明

production hook、CLI、`scripts/lib/` の実行ロジックは変更しない。現行の `scripts/ci/audit-harness-contract.js` は既知失敗機構の存在を要求しているため、既知失敗機構の不在と catalog の整合性を検査する test-only contract へ更新する。

## 実施フロー

1. 現行テストを残す契約へ対応付け、keep、merge、delete に分類し、全既知失敗の disposition を記録する
2. 単一 catalog を導入し、現行 suite の所属を移す
3. 巨大テストから、残す契約に対応する代表ケースを先に確保する
4. 重複、実装形状、偶発的挙動、未登録テスト、および disposition が「契約外・古い期待」または「代表テストへ統合済み」と確定した既知失敗を削除する
5. test script と README の説明を新しい suite 構造に合わせる
6. 削除前後の行数、テスト数、実行時間、skip 数、契約対応表を記録する

各段階で `npm test` を実行し、最後に `npm run test:full` を実行する。削減作業中に本体の実行時挙動を変更する必要が生じた場合は、その変更をこの作業へ混ぜず、別タスクとして切り出す。

## エラーと安全上の懸念の扱い

テストが現在の危険な挙動を肯定している場合、そのテストを互換契約として残さない。ただし、安全上の懸念自体は失わないよう、追跡 ID 付きの別タスクとして記録する。その挙動が残す契約への違反である場合は、別タスクでの修正が完了するまで削減完了をブロックする。契約自体を変更する場合は、本設計の再承認を必要とする。

現時点で候補となる例は、package manager command 構築での path traversal や改行入力の許容である。今回の削減では本体挙動を変更せず、必要な修正と望ましい契約テストは別タスクで扱う。

一時ファイルを使うテストは `finally` 相当の処理で後始末する。保持したテストの失敗は非ゼロ終了にし、stderr の警告を成功扱いの出力へ埋没させない。

## 計測方法

基準 commit は `3a5b29b1e47b1cb8ec3048eb2d7bf23f30f4ddb0` とする。基準値 26,515 行は、次のコマンドで `tests/` 配下の全 JavaScript を対象に計測した値である。

```bash
find tests -type f -name '*.js' -exec wc -l {} + | tail -n 1
```

テストファイル数は次で計測する。

```bash
find tests -type f -name '*.test.js' | wc -l
```

テスト case 数は `node tests/run-all.js --suite full` が出力する aggregate count を正とし、validator と smoke の成否は別に記録する。runner は保持する全テストファイルについて同じ集計形式を出力しなければならない。

実行時間は、同じ端末で他の harness test を並列実行せず、次の各コマンドを連続 3 回実行した `real` の中央値とする。

```bash
/usr/bin/time -p npm test
/usr/bin/time -p npm run test:full
```

baseline と final は、それぞれ対象 commit の clean worktree で計測する。両方で `npm ci` を実行し、同一端末、同一 Node.js/npm version、同一条件でテストを実行する。計測前の `git status --porcelain` は空でなければならない。

verification evidence には、baseline と final の commit hash、依存関係準備コマンド、clean 状態、計測コマンド、3 回分の raw output、中央値、`node --version`、`npm --version`、`uname -s`、`uname -m`、macOS では `sw_vers -productVersion` を記録する。hostname、ユーザー名、絶対パスなどの個人情報は保存せず、外部コマンドの出力に含まれる場合は redact する。この設計時点の標準 verification 環境は macOS arm64、Node.js `v22.20.0`、npm `10.9.3` とし、この環境では `required` テストの skip を 0 件にする。

## 完了条件

- `tests/` の JavaScript 行数が 7,955〜13,257 行である
- 削減率が基準値 26,515 行に対して 50〜70% である
- `npm test` が成功する
- `npm run test:full` が成功する
- 許容済み失敗が 0 件である
- 全既知失敗の disposition と必要な追跡先が記録されている
- suite 未登録テストが 0 件である
- すべての「残す契約」に `required` テストが最低 1 件対応している
- 標準 verification 環境で `required` テストの skip が 0 件である
- `optional` テストの skip 件数と理由が記録されている
- 残す契約とテストの対応を説明できる
- 本体の実行時挙動に変更がない
- 定義済みの計測方法による削除前後の行数、テストファイル数、test case 数、実行時間が verification evidence に記録されている

## 採否

- 採用: 契約中心の 3 層構造、50〜70% 削減、単一 catalog、既知失敗の廃止
- 保留: package manager command 構築など、本体コード側の安全修正
- 却下: 単純な時系列削除、coverage 数値維持、integration のみへ全面集約

# 段4にセキュリティとコメントの検査を入れる

## Objective

ライフサイクル段4（確かめる）に、**セキュリティ**と**コメントの過不足**を明示的な検査として置く。
どちらも「1語の箇条書き」ではなく、手順と証拠要求を持つ形にする。

## なぜ今これか

**セキュリティは既に `commands/review-task.md` の項目にあった。** ただし
`   - security` という1語の箇条書きで、何をするか・何を残すかが書かれていなかった。

結果として `scripts/lib/permission-resolver.js` の auto-allow バイパス
（`git status && rm -Rf ~` が無警告通過）は、そのファイルが作られてから 2026-08-18 まで
どのレビューにも引っかからなかった。見つかったのは**コードを読んだからではなく、
敵対的な入力で分類器を実行したから**。

つまり足りなかったのは「security を見る」という意識ではなく、**境界を叩く手順**だった。

**コメントは項目自体が無かった。** 2026-08-17 のセッションで、私は経緯をコード内に
159行書き、既存比率（9〜14%）に対し26%まで膨らませた。レビューでは検出されず、
指摘されて初めて気づいた。

## Non-goals

- **全変更に対してセキュリティレビューを必須にしない。** doc だけの変更に
  「該当なし」を書かせるのは、満たしようのないゲートを増やすのと同じ失敗になる
- **コメント比率に閾値を設けない。** 2026-08-17 に `commands/verify.md` から
  達成不能な coverage 80% 目標を外したばかりで、同じ形を持ち込まない。
  測って差分を報告するところまでにする
- `agents/code-reviewer.md` と `skills/code-review` は書き換えない。段4から名指しするだけ
- 新しいコマンドは作らない。段4の入口は `/verify` と `/review-task` のまま

## 決定

**1. セキュリティ検査は「触ったか」で条件づける。**

必須になるのは、変更が次のいずれかに触れた場合。

- 許可・認証・権限の判定（allow / deny を返すコード）
- 信頼できない入力のパース（コマンド文字列、ユーザー入力、外部レスポンス）
- シェル / SQL / パスの組み立て
- 秘密情報、認証情報、トークンの取り扱い
- ネットワーク送信先の決定

触れていない場合は `Security` 節に「該当面に触れていない」と1行書いて終わり。
**触れた場合は、コードを読むだけでは足りない。**

**2. セキュリティ検査の証拠は「叩いた結果」にする。**

allow/deny を返すコードを変えたなら、**敵対的な入力で実行し、入出力の表を残す**。
今回の穴を見つけたのはこの方法で、コードの読み直しでは3ヶ月見つからなかった。

叩く観点（最低限）: 大小文字、フラグの並び順、区切り文字での連結、引用符、
コマンド置換、境界値（空・極大）。

**3. コメント検査は「年表かどうか」で見る。**

- **落とす**: いつ何を撤去したかの経緯。それは `docs/design/` の役目で、
  コードに書くと契約が2箇所になる
- **残す**: コードだけからは読めない実装判断（なぜこの条件か、なぜこの順序か）
- **足す**: 非自明な判断が無説明で入っている箇所

比率は `docs/how-to/` に測り方を置き、**基準からの乖離が大きい時に理由を書く**。
閾値では止めない。

**4. 置き場所は `review-summary.md` の新しい2節。**

`Security` と `Comment Adequacy` を canonical セクションに足す。
`parseReviewState` の必須節（`Review Scope` / `Findings` / `Residual Risks` / `Next Action`）は
変えないので、パーサへの影響は無い。

## 却下した案

| 案 | 却下の理由 |
|---|---|
| `/verify` にコメント比率のゲートを足す | 閾値が恣意的になる。coverage 80% を外した直後に同じ形を作ることになる |
| セキュリティ専用コマンドを新設する | 段4の入口が3つになる。未記載コマンドが23本ある状態で入口を増やさない |
| `security` の箇条書きに文言を足すだけ | 今回の失敗はまさにそれが効かなかったこと。証拠要求が無いと実行されない |
| 全変更でセキュリティ節を必須にする | doc 変更に「該当なし」を書かせるのは vacuous なゲート |
| `agents/code-reviewer` の自動起動 | エージェント起動は明示指示がある時だけ、という運用と衝突する |

## 触る対象

- `commands/review-task.md` — 検査項目に手順と証拠要求を持たせる
- `templates/review-summary-template.md` — `Security` / `Comment Adequacy` 節を追加
- `commands/COMMANDS.md` — 段8の説明
- `docs/how-to/run-a-task.md` — 段4のチェックリストと、コメント比率の測り方
- `CLAUDE.md` — Preferred Commands の段4

**契約が変わるもの**: `review-summary.md` の canonical セクション集合。
`parseReviewState` の必須節は変えないので機械的な互換性は保たれる。

## 数字

- 今回の穴が見つかった方法: 敵対的入力13件を分類器に通し、6件が `ALLOW` だった
- 2026-08-17 のコメント比率: 26%（既存基準 9〜14%）。指摘されるまで検出されなかった

## 許容したリスク・負債

- **「触ったか」の判定は人が行う。** 機械的に diff から判定していないので、
  見落とせばセキュリティ節は「該当なし」で通る。監査で検出できない
- **コメント検査は判断に依存する。** 「年表か実装判断か」の線引きは自動化していない

## Open Issues

- `agents/code-reviewer.md` の Security 節と、ここに書く観点が重複していないか未確認（推定: 重複する）
- 段4で refactor した場合に `/verify` をやり直す規則があるが、セキュリティ検査も
  やり直すべきかを書いていない（推定: 敵対的入力の表は再実行が安い）

# 文書が主張する強制と実装の乖離を解消する

日付: 2026-08-12

## Objective

ライフサイクル文書が「機構が強制する」と書いている箇所を実装と突き合わせ、嘘を消すか機構を作るかで揃える。

## なぜ今これか

`HARNESS_OVERVIEW.md` の記述を実測で検証したところ、中核（完了宣言が唯一のブロック、編集/コミットは advisory）は
文書どおりだった一方、5件の乖離が出た。うち2件は**常時ロードされる文書**にあり、毎セッション「存在しない制約」が
事実として注入されていた。読み手はそれを検証しないので、嘘の doc は無い doc より悪い。

## Non-goals

- 強制主張60行の全数照合（機構を名指しする記述のみ扱う。規律の宣言は強制されなくても嘘ではない）
- `run-with-flags` 機構そのものの撤去（`minimal` / `standard` の2段は意味を保つ）
- `scripts/engine-adapter.ts` / ECC skills 44本 / 学習ループ

## 判明した具体的な欠陥

1. **撤去済みの編集ブロックが3箇所で現役と書かれていた。** `rules/common/documentation.md:50,53` と
   `AGENTS.md:76`。2026-07-28 に advisory 化したが、文書は2週間そのままだった。前2つは常時ロードされる。
2. **`main`/`master` への push 禁止が一度も発火していなかった。** 唯一の push フックはブランチを見ずに
   定型文を出すだけで、しかも `strict` プロファイル限定。`ECC_HOOK_PROFILE` を設定するコードは存在せず、
   既定は `standard`。「常時禁止」と書かれた規則を守らせるものが何も無い状態だった。
3. **SessionStart が13日前の `run_state` を現在として注入していた。** `verify_present` 等は前の行から
   持ち越されるだけで実ファイルから再導出されない。加えて `if (persistedState) ... else if (artifactContext)`
   の順序により、DB に行があると実態側の判定に永久に到達しなかった。
4. **`Write` が品質フックを素通りしていた。** matcher が `Edit` のみ。テレメトリ上、ファイル変更の47%
   （4,363 / 9,319）が format・typecheck・console.log 検査を通っていなかった。`MultiEdit` は31,945件中0件で、
   存在しないツールが matcher に残っていた。
5. **`OPERATING_MODEL.md:124` が advisory の commit ゲートを `Enforced Now` に載せていた。**

作業中に発見して合意のうえ追加で直したもの:

6. **`npm test` が実リポジトリの `progress.md` を上書きしていた。** `pre-compact.js` と `subagent-stop.js` は
   cwd のリポジトリに書く。テストヘルパ `runScript` が cwd を渡さないため、テスト実行のたびに本物の
   セッション状態がフィクスチャ値（`agent=docs-writer` 等）に置き換わっていた。安全な `runScriptInDir` は
   同じファイルに既に存在していた。
7. **`session-start.js` の cross-repo フォールバックがライブラリの契約を打ち消していた。**
   `getLatestRunState` は「別リポジトリの状態を拾ってはいけない」とテストで契約化されているのに、
   `|| getLatestRunState()` が repo_root 指定を無効化していた。
8. **`repo_root` の symlink 未正規化。** `git rev-parse --show-toplevel` は `/private/var` を返し、
   呼び出し側は `/var` を渡しうる。7 のフォールバック撤去で初めて表面化した。

## 決定

方向は項目ごとに決めた。一括にすると、リスクゼロの文書修正と毎セッションの挙動が変わる変更が同じ承認に乗る。

| 項目 | 方向 |
|---|---|
| 1, 5 | 文書 -> 実態。撤去は意図的な決定で理由も記録済み |
| 2 | **実態 -> 文書。実ブロックを新設**（`hooks/git-push-guard.js`） |
| 3, 4, 6, 7, 8 | 実態 -> 文書。仕様ではなくバグ |

push ブロックだけが本物の設計判断だった。「完了宣言が唯一のブロック」という設計と衝突して見えるが、
**軸が2本あるだけ**と整理した。完了ゲートはライフサイクル成果物チェーンの話で、push は外向き操作の話である。
各軸で最も不可逆な一点だけを止める、という原則は保たれる。

実装で外せなかった条件が1つある。**引数なしの `git push` を捕まえること。** コマンド文字列に `main` は
現れないので、正規表現では最も普通のケースを取り逃がす。リポジトリからブランチを解決する必要があり、
半分しか捕まえないガードは 2026-07-28 に学んだ「空虚に満たせるゲート」そのものになる。

## 却下した案

- **鮮度カットオフ（N日より古い `run_state` を無視）**: 年齢は代理指標。成果物が残る6ヶ月前の行は再開可能で、
  成果物が消えた1時間前の行は再開不能。実在が本当の信号なので、カットオフは正しい行を捨てる誤りを新たに作る
- **`run_state` 注入の廃止**: `CLAUDE.md` が SQLite を runtime source of truth と位置づけた意図的な設計。
  バグは無条件に信じることと実態側を影に追いやることであって、DB を見ること自体ではない
- **`permissions.deny` で push を止める**: コマンド文字列マッチなので暗黙 push を捕まえられない
- **`runScript` の既定 cwd を一時ディレクトリにする**: 166箇所に影響する。progress.md を書く2フックの
  12箇所だけを差し替えた

## 検証

- `npm test`: 1284 -> 1322 passed / 0 failed（新規38件）
- push ガード30件は正常系・境界（`maintenance` / `mainline` / `--dry-run`）・異常系（非リポジトリ・壊れた入力）を含む
- 契約監査の不在 assert が実際に再発を捕まえることを、嘘を一時的に復活させて確認した
- `progress.md` の md5 がテスト実行前後で不変であることを確認した
